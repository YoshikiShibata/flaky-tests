# flaky-tests

E2E テスト・並列実行環境で発生した flaky test の事例と対策パターン集。

## 索引

### テスト分離・並列実行

- [全データ更新ジョブによるテスト間干渉](./global-data-modification-interference.md) — 全行 `InsertOrUpdate` するジョブテストが、他テストのセットアップデータを上書きする
- [グローバル集計値の before/after 比較が並行書き込みで揺れる](./global-aggregate-before-after-assertion.md) — 「操作が状態を変えないこと」を全件横断 API の件数 before/after 比較で検証していたため、無関係な並行テストが 2 スナップショットの間に集計対象行を commit すると ±1 のズレで、実行のたびに成功したり失敗したりする（flaky）。誰も他人のデータを壊していないのにアサーションのスコープが広すぎて壊れる型。対象 API が正当にグローバルなのでロックではなく「観測を自テストのエンティティに絞る＋件数でなく ID 集合の同一性で比較」で決定化
- [テストデータのハードコード値とドメイン定数の不一致](./hardcoded-domain-values-in-test-data.md) — 不正値が DB に残り、別テストの全件取得 API で変換エラーになる
- [意味を持つ固定値が主キーのグローバルテーブルは、キー空間をテストごとに分割しないと衝突する](./fixed-key-collision-in-shared-keyspace.md) — 主キーが発効時刻・境界値・年などの「意味を持つ値」だと、値そのものが検証の一部なので **UUID 化による衝突回避が使えない**。結果キーはリテラルで書かれ、兄弟テストからのコピペで**同じ値が複数のテストに現れる**。壊れ方は 2 つで、seed の主キー衝突（loud）と、`t.Cleanup` の Delete が実行中の別テストの行を消す横取り削除（silent）。`InsertOrUpdate` 化は前者だけを消して後者を残すので不十分。共有したい状態は無いためロックは並列度を捨てるだけで根治せず、「不在」を主張するテストはロックでは救えない。対策は**キー空間の分割**（テスト名をキーにした割り当て表 + 値はテスト名からしか引けない構造 + 重複を機械検査）。時刻キーは `time.Time` の構造体等価だと別 location の同一瞬間をすり抜ける／`UnixNano` は 1678〜2262 年外で未定義。sentinel（「まだ何も無い」時刻）は割り当て表の外（seed・マイグレーション）から崩されるので実行時に前提を確認する ― **崩れたとき loud に落ちる消費者と silent に通る消費者が混在する**。フレーク率を周回数で割って新規テストの高頻度フレークを低頻度と誤認しない、CI の `-parallel=1` は分離欠陥を隠す、対策は変異テストで発火を確認する、も収録
- [プロセス共有キャッシュによる test-scoped fake override の無効化](./process-shared-cache-vs-tid-scoped-fake.md) — サービス側のキャッシュが tid スコープ fake を貫通してしまう
- [プロセス共有 singleflight がリーダーの ctx キャンセルを無関係なフォロワーへ伝搬させる](./singleflight-shared-ctx-cancellation-propagation.md) — `Do` の中で呼び出し元スコープの ctx を使うと、あるリクエスト（errgroup 兄弟エラー／クライアント切断）のキャンセルが、同じキーを待つ無関係なリクエストを `context canceled` で巻き込む。発生源は errgroup 先着エラーに握り潰され、被害はフォロワー側にだけ表面化する
- [キャッシュ／singleflight のキーが「結果が依存する入力」を取りこぼす](./coalescing-cache-key-omits-result-dependency.md) — 共有キャッシュ／inflight のキーが種別 enum しか含まず、結果が依存する `now`（時刻）を落としていると、debug-time で `now` を大きくずらしたテストが waiter として合流したとき leader（実時刻）の結果を無検証で受け取り、自分の入力では本来ありえない結果（期待要素の nil／空）を掴む。「キーは結果が依存する入力の全体でなければならない」型。`now` を TTL 幅のバケットに切り捨ててキーへ含めることで、本番挙動を変えずに決定化。本番実害は無いが設計欠陥なのでプロダクト側で修正
- [逐次ループの並行化におけるループキャリー依存性の見落とし](./loop-carried-dependency-in-concurrent-test-setup.md) — 並行ループ化で暗黙の実行順序依存が壊れる
- [セットアップ・クリーンアップの順序が引き起こす孤立参照](./setup-cleanup-order-orphan-reference.md) — Child→Parent の順で setup すると、LIFO cleanup により「Child は存在するが参照先 Parent が存在しない」状態が発生する。逆向き（親が残って子が無い）も同じ症状を起こす: 後片付けは参照整合性に従って子から削除するため親行の削除が最後の別コミットになり、「親は走査の述語を満たすのに子が無い」中間状態を並行のグローバル走査が踏む。親を先に消せないので順序入れ替えでは直せず、削除前に親を述語から外す（同一トランザクションで）＋ 走査と後片付けを排他する、の 2 段構えになる
- [並行取得の「先着エラー」非決定性とエラー→ステータスマッピングの取りこぼし](./errgroup-first-error-status-mapping-gap.md) — errgroup が返す先着エラーが非決定的で、マッピング層が一部センチネルを取りこぼすと観測ステータスが揺れる
- [共有フィクスチャプールの再利用による残留状態の干渉](./shared-fixture-pool-residual-state.md) — 再利用される共有プールが過去テストの副作用を蓄積したエンティティを配り、「初期状態」前提のテストが偽陰性で flaky になる
- [テストヘルパーの「直接DB→API/usecase経由」化が生む隠れた共有依存とロック抜け](./helper-api-routing-hidden-shared-dependency.md) — ヘルパーを本物のリクエスト処理経由に変えると、その処理が読む共有マスタへの依存とロック義務が暗黙に増え、削除窓と競合してフレークになる
- [状態共有する逐次サブテストの途中失敗によるカスケード失敗](./stateful-sequential-subtests-cascade-on-midstep-failure.md) — `t.Run` で区切った状態累積の逐次シナリオで、途中 1 ステップのフレーク失敗が後続の off-by-one 連鎖失敗を量産し原因が埋もれる。`t.Fatalf` は親ループを止めないため、失敗時 `break` で打ち切る

### 時刻・境界

- [時刻境界で失敗するフレーキーテストの原因と対策](./flaky-test-time-boundary-patterns.md) — クライアント／サーバーの時刻計算ずれ
- [現在時刻から導出される値のハードコードによる Flaky Test](./hardcoded-season-from-current-time.md) — 季節・期間区分などをハードコードしている
- [月末境界による Flaky Test：月別設定値の切り替わり](./month_boundary_master_data_switch.md) — 月をまたぐとマスターデータが切り替わる
- [月単位の日付演算が正規化で繰り上がり、「前月」が「当月」になる](./month-arithmetic-normalization-overflow.md) — `AddDate(0, -1, 0)` は存在しない日付を静かに正規化する（`6/31` → `7/1`）ため、月末日を起点にすると「前月」が当月になる。年月の一致で計上を決めるロジックの検証が反転し、フレークの顔をして落ちるが、実は年 7 日（3/29〜31・5/31・7/31・10/31・12/31）だけ 100% 失敗する決定的バグ。対策は「日を 1 に丸めてから月を加減算する」＋判定側の `now` を注入して固定。連続ループの 1 回だけ落ちたときに累積劣化と誤診しないための切り分け手順と、修正前の形に戻して失敗を再現する空振り確認付き
- [業務時間境界をまたぐテストデータによるフレーキーテスト](./time-frame-boundary-crossing.md) — 相対時刻がドメイン固有の日付境界をまたぐ
- [テストデータの有効期限が次の暦境界とちょうど一致するパターン](./data-lifetime-aligned-to-day-boundary.md) — 暦境界アンカーの StartTime と整数倍 duration の組み合わせで、テスト実行中の境界跨ぎでデータが消失する
- [壁時計の後方ステップ（NTP補正）による順序依存テストのフレーキー失敗](./wallclock-backward-step-by-ntp.md) — NTP補正で `time.Now()` が後方ジャンプし、作成時刻DESCソートが作成順前提と食い違う。macOS `timed` ログでの追跡方法付き
- [deadline 到達時のステータスコードは client timer と server 応答のレースで揺れる](./deadline-arrival-status-race-client-vs-server.md) — gRPC は deadline を server へ伝播するため、期限の瞬間に両端のタイマーが同時に切れる。client 側 timer が勝てば `DeadlineExceeded`、server が ctx エラーを retriable 分類して返す応答が先着すれば `Unavailable`。`D_server ≥ D_client` なので通常は client が勝つが、マージンは µs〜ms しかなく高負荷時のスケジューリング遅延で逆転する。単一コードへの固定アサートをやめ、緩めた検出力は「経過時間が deadline に達したか」で補う

### クエリ・データ意味論

- [DB クエリの LIMIT と後フィルタリングによるフレーキーテスト](./db_query_limit_with_post_filtering.md) — 小さい LIMIT がフィルタ後 0 件を引き起こす
- [keyset ページネーションの tie-breaker 欠如による行の取りこぼし](./keyset-pagination-missing-tiebreaker.md) — 非一意なソートキー（`CreateTime`）に strict `<` だけで cursor を組むと、同値行がページ境界で脱落する。間欠的な E2E 失敗が、テストのフレークではなくサービス側のページネーション実装バグを検出していた事例
- [複数スナップショットで組み立てる読み取りが「どの時点にも存在しなかった状態」を観測する](./multi-snapshot-read-composes-nonexistent-state.md) — 1 つの結果を返す読み取りが「一覧を引く → その ID で参照先を引く → 同じ ID で件数を数える」のように**複数回に分けて読み**、各読み取りが独立したスナップショットで走ると、読み取りの合間に入った削除により**単一のコミット時点としては存在し得ない組み合わせ**（要素はあるが参照先が無い／参照先はあるが件数 0）を観測する。**書き込み側が 1 トランザクションで原子的に削除していても防げない**（窓は読み取り側にあり、原子性は複数時点を読む相手を守らない）。欠損を「あり得ない不整合」として fail loud する実装だと、正常な並行削除のたびに 500 を返すバグになる ― **fail loud は「起こり得ない」の判定精度に全面的に依存する**。リポジトリのメソッドが呼び出しごとにトランザクションを開く構造は呼び出し側から見えないため、「読み取りだけだからトランザクション不要」という既定判断に落ちる（あるサービスでは usecase の tx 121 箇所中、読み取り専用は 2 箇所）。窓は読み取りの間に N-1 個あり、削除が入る位置で別のエラーメッセージになるので**同一原因が別バグに見える**。並列 E2E は本番より衝突頻度が桁違いに高く、低頻度フレークとして先に現れる（環境要因で閉じると早期警告を捨てる）。テスト側のロック・後片付け順序・リトライでは直らず、対策は読み取りを 1 スナップショットに束ねること。衝突操作を並走させる再現テストの作り方（1 試行あたりの命中率の実測・空振り防止の 2 ガード・変異テストでの検証力確認）と、誤診（分離不足／残留データ／エミュレータ劣化）の切り分け手順も収録

### DB 実装依存（エミュレータ vs 本番エンジン）

- [テスト用DBエミュレータと本番DBエンジンの挙動差で表面化する flaky](./emulator-vs-production-db-divergence.md) — エミュレータの緩い「行順序」「分離レベル」が潜在的な非決定性を覆い隠し、本番相当 DB でのみ flaky に落ちる。(1) ORDER BY 無しクエリ × 固定順アサーション、(2) 並行入金に依存した残高がタイミングで枯渇、の2事例
- [エミュレータの直列化に隠されていた並列サブテストのデータ競合](./data-race-masked-by-emulator-serialization.md) — `t.Parallel()` サブテストが外側スコープの共有変数（`err`）に両方から書き込むデータ競合。エミュレータの RW トランザクション直列化により 2 処理が同時並行にならず、周囲の同期（atomic カウンタ・gRPC）と相まって happens-before で順序付いていたため `-race` でも長期間検出されず、本番相当エンジン（Omni）の並行実行で初めて顕在化。1 件の競合で多数のテストが連鎖 FAIL する
- [トランザクション内の retryable エラー（Aborted）握りつぶしがクライアント自動リトライを無効化する](./swallowed-in-tx-retryable-error-defeats-client-retry.md) — tx コールバック内で read の `Aborted` をログして `return nil` で握りつぶすと、クライアントの自動リトライが発火せず abort 済み tx のまま commit に進む。緩いエミュレータはこの commit をサイレントに受理してバグを隠し、厳密な本番相当エンジンは非 retryable エラー（precommit token 欠如）で拒否して致命的に失敗する。本番相当エンジンが正しく／エミュレータが不正という構図の反転が学びの核
- [トランザクション再試行で使い回すモデルへの ID 書き戻しが INSERT を UPDATE に転落させる](./tx-retry-model-mutation-flips-insert-to-update.md) — クライアント管理リトライはコールバックを丸ごと再実行するが、捕捉した可変オブジェクトはリセットされない。「保存時に採番 ID を引数へ書き戻す」副作用が Aborted 再試行をまたいで残り、2 回目は ID 有→ UPDATE に転落して `row not found`。低負荷では通り高負荷で間欠失敗する。冪等化（試行冒頭で状態復元）で解消

### テスト基盤・コンテナ実行環境

- [エミュレータへの書き込みが単一コネクションの転送スタックで稀にタイムアウトする](./single-connection-stall-hangs-fixed-deadline-write.md) — ホスト→コンテナの `localhost` 接続が通るユーザーランドのポートフォワード中継が、高い接続生成レートのピークで**特定の 1 本のフローだけ**を宙吊りにし、書き込みの `Close` が固定タイムアウトで `context deadline exceeded` に落ちる。エミュレータ自体は健全（同時刻に毎秒数百件を処理）でサーバ側ログが「1 本だけ孤立して滞留」を裏付ける。先に fsync を**仮説**として memory backend 化し高頻度は見かけ上収まったが、その仮説は未検証のまま低頻度で再発。「インメモリなのに固定タイムアウト張り付き」の矛盾が、証拠で裏を取れる真因（転送ハング）に気づく鍵に——**妥当そうな修正で症状が消えても真因を証明したことにはならない**という教訓付き。対策は単発タイムアウト延長ではなく**短タイムアウト × 新コネクションでのリトライ**。多重化 gRPC 系が同症状を起こしにくい理由も整理
- [ホスト名で張った gRPC 接続の初回 DNS 解決が per-call 締切を食い潰す](./hostname-dial-defers-dns-into-per-call-deadline.md) — ローカル fake を `localhost:<port>` で dial すると dns resolver 経由になり、名前解決は**初回 RPC 時に per-call 締切の中で**実行される。`lookupHost` と service config 用 TXT（`_grpc_config.localhost`、既定有効・`/etc/hosts` に無いので必ずネットワークへ出る）を逐次実行し両方終わるまでアドレスを 1 つも返さないため、解決が数秒スタックするとリクエストは**ワイヤに乗る前に**締切を使い切る。fail-fast は初回解決中には効かないので返るのは `Unavailable` ではなく `DeadlineExceeded` で、「サーバが遅い / 接続できない / fake が listen していない」へ誤誘導される。`grpc.NewClient` は dns 既定・`grpc.DialContext` は passthrough 既定なので**同じターゲット文字列でも API 次第**（`Dial`→`NewClient` 移行で静かに踏む）。決定的な切り分けは「注入エラーがタイムアウトする＝ハンドラ非到達」と `Channel exiting idle mode`→`Resolver state updated` の間隔（grpclog は既定で INFO/WARNING を捨てるので計装が必須）。落ちるのは締切予算がストールより短い経路だけで、アプリ層リトライは同じ解決を待つので無効。対策は締切の padding ではなく IP リテラル化（`deadResolver` で resolver を迂回）。「一斉に同時刻で失敗」を計算で検証したら揃っていたのは開始時刻で診断の向きが反転した件、`Unavailable` 注入テストが本物のストールで偽陽性 PASS していた件も収録
- [テストランナーの結果キャッシュがヒットして「テストの副作用」が実行されない](./test-cache-hit-skips-server-startup-side-effect.md) — E2E ハーネスが被テストサーバの起動手段としてテストランナー（`go test`）を流用していると、結果キャッシュがヒットした回だけ前回の出力を再生して即 exit 0 し、サーバが一度も起動せず「ready にならない」で全体が落ちる。`FAIL:` 行はゼロなのでテストコードを読んでも原因が無く、出力の内部矛盾（27 秒の試行に 301 秒の PASS・22 分前のログ・`(cached)`）だけが証拠。キャッシュ照合は「テストが読んだ環境変数の現在値」で決まり、fake の動的ポートが毎回変わるおかげで**偶然ミスして動いていた**構成だった。macOS のエフェメラルポートはプロセス横断の単調増加カウンタで、E2E 1 周がちょうど 1 周分ラップするためポートは毎周 100〜700 しかずれず、ずれが 0 になった周で発火（数百周に 1 回）。対策は `-count=1` + ハーネス側で「ready 通知なしの exit 0」をエラー化。調査手順（キャッシュ実装の読み方・`GODEBUG=gocachetest=1` での差分実験・ログからのポート時系列抽出・OS 割り当ての実測）を一般化して収録

### 開発プロセス・PR 分割

- [単独で検証できない単位への PR 分割が、統合時にしか現れない不整合を「フレーク」として噴き出させる](./contract-change-split-across-unverifiable-prs.md) — 値の**意味**を変える変更を「契約（スキーマのコメント・仕様書）だけの PR」「実装追随の PR」「その値を検証するテストを追加する PR」の 3 本に分割し、互いの変更を base に含めずにマージすると、各 PR の CI は全て緑なのに統合状態だけが 100% 失敗する。テストを 1 本も含まない契約変更 PR は CI にとって no-op で、意味の反転は型でもコンパイルでも捕まらないため、唯一の検出器は「契約から書かれたテスト」だけになる。失敗は統合ブランチを取り込んだ人のローカルで「長時間ループの N 周目から突然落ちる」フレークそっくりの顔をして現れ、上流が直すと勝手に消えるので原因（分割の粒度）が記録されない。期待値と実測値が**補数関係**（和が満点）なのが意味反転のサイン。分割の基準は行数ではなく**単独で検証可能か**、要求すべきは「各 PR が緑」ではなく「マージされる形の組み合わせが緑」
- [文字列キーで疎結合された設定の改名が、参照側に届かず既定値へ静かに落ちる](./renamed-string-key-falls-back-to-default-instead-of-erroring.md) — feature flag・環境変数・DI キーのように**文字列キー**で参照される設定を改名したとき、参照側（とくにテストが値を注入する専用経路がキー文字列を**複製**している場合）に改名が届いていないと、設定解決層は不一致をエラーにせず**既定値へフォールバック**する。既定値は安全側（無効・0）なので、設定ミスが「機能を止めているときの正しい挙動」と区別できず、監視にもログにも異常が出ない。結果、失敗は**非対称**になる ―「機能が有効な前提のケースだけ落ち、既定値を期待するケースは通る」。通ったケースのほうが問題で、**否定側の期待値だけで構成されたテストは入力が一切届かなくても緑になる**（偽陰性）。実測値が一律に既定値へ揃い、かつ他経路が出すはずのエラーログが皆無なら「値の計算ミス」ではなく「入力の不着」を疑う。意味の反転と違い **grep で静的に検出できる**型なので、対策は「キー定数を共有して複製させない」「テスト専用の注入経路に限り未知キーをエラーにする」「肯定ケースを必ず 1 本入れる」。段階移行で改名だけ先に入ると新旧どちらの解決層にも到達しない**制御不能な区間**が生まれる点、疎通確認ログを実際の呼び出しと違う経路で取ると「ログは有効・実挙動は無効」の乖離で調査が迷子になる点も収録。「消費側テストがあるのになぜ CI で止まらないのか」にも答えている ― 変更単位の CI は**イベント時点の base** で走り base が進んでも再実行されないため、緑は「過去のある時点の base での緑」でしかない。滞留期間がそのまま結果の古さになり、base 最新要求・マージキューが無ければ任意に古い緑のままマージできる（auto-merge はそれを自動化する）。**CI 完了時刻とマージ時刻の差**で機械的に検出可能
